# 1. Cloud Concepts

## What is Cloud Computing?
Delivery of computing services — servers, storage, databases, networking, software, analytics — over the internet ("the cloud") with pay-as-you-go pricing.

## Benefits of Cloud Computing (Azure's 6 Core Benefits)

1. **High Availability** — Services remain available with minimal downtime (defined by SLAs)
2. **Scalability** — Add resources to meet demand (vertical or horizontal)
3. **Elasticity** — Auto-scale up/down dynamically
4. **Agility** — Rapidly deploy and configure resources
5. **Geo-distribution** — Deploy globally to reduce latency
6. **Disaster Recovery** — Replicate data to protect against failures

## CapEx vs OpEx

| | CapEx (Capital Expenditure) | OpEx (Operational Expenditure) |
|--|--|--|
| **Definition** | Upfront investment in physical infrastructure | Pay-as-you-go for services |
| **Example** | Buying servers, building a data center | Azure monthly bill |
| **Cloud Model** | On-premises / Private Cloud | Public Cloud |
| **Tax** | Deducted over time (depreciation) | Deducted in same year |

> **Cloud = OpEx model** — shift from owning to renting infrastructure.

## Consumption-Based Model
- No upfront costs
- No wasted resources
- Pay for what you use, stop paying when you stop using

---

## Cloud Service Models

| Model | You Manage | Azure Manages | Azure Example |
|-------|-----------|---------------|---------------|
| **IaaS** | OS, Apps, Data | Hardware, Network, Virtualization | Azure VMs, Azure Disk |
| **PaaS** | Application, Data | OS, Runtime, Middleware, Hardware | Azure App Service, Azure SQL |
| **SaaS** | Nothing | Everything | Microsoft 365, Dynamics 365 |

### Shared Responsibility Model

```
On-Premises: YOU manage everything

IaaS:
  Azure manages → Physical hosts, network, data center
  You manage   → OS, middleware, runtime, apps, data, identity

PaaS:
  Azure manages → Physical + OS + middleware + runtime
  You manage   → Applications, data, identity

SaaS:
  Azure manages → Almost everything
  You manage   → Data, identity, devices, accounts
```

> **Always your responsibility regardless of model:**
> - Identity and access management
> - Devices (mobile and PCs)
> - Your data and information

# 2. Azure Global Infrastructure

## Geographies
A discrete market (typically a country or region) that preserves data residency and compliance boundaries.

## Regions
- A **region** is a set of data centers deployed within a latency-defined perimeter, connected via a dedicated regional low-latency network
- Azure has **60+ regions** across 140+ countries
- Each region is paired with another region (**Region Pair**) for disaster recovery

### Region Pairs
- At least **300 miles apart**
- Replicate data automatically for some services
- Prioritized recovery in outages
- Updates rolled out one region at a time
- Example: East US ↔ West US | North Europe ↔ West Europe

### Special Regions
- **Azure Government** — US government only (FedRAMP, DoD compliance)
- **Azure China** — Operated by 21Vianet, separate from global Azure
- **Sovereign Regions** — Isolated from main Azure cloud

---

## Availability Zones
- Physically separate data centers within a region
- Each has independent power, cooling, networking
- Minimum **3 zones** per supported region
- Connected via high-speed fiber (< 2ms latency)
- Protects against **data center failures**

### Zone-Redundant vs Zonal Services
- **Zonal** — Pin resource to a specific zone (VM in Zone 1)
- **Zone-redundant** — Replicated automatically across zones (Zone-redundant Storage)
- **Non-regional** — Always available globally (Azure Active Directory)

---

## Azure Data Centers
Physical buildings containing the servers. Not directly accessible by customers.

## Azure Edge Zones
Extensions of Azure placed in metro areas for ultra-low latency (similar to AWS Local Zones).

# 3. Core Compute Services

## Azure Virtual Machines (VMs)
IaaS — full control over OS, software, and configuration.

- Choose from Windows or Linux
- Multiple sizes: General Purpose, Compute Optimized, Memory Optimized, Storage Optimized, GPU
- Billed per second (when running)

### VM Availability Options

| Option | Protection Level | SLA |
|--------|-----------------|-----|
| **Single VM (Premium SSD)** | Single DC | 99.9% |
| **Availability Set** | Rack-level (fault + update domains) | 99.95% |
| **Availability Zone** | Data center-level | 99.99% |

### VM Scale Sets (VMSS)
- Automatically create and manage a group of identical VMs
- Auto-scale based on demand
- Distributes VMs across availability zones

### Azure Dedicated Hosts
- Physical server dedicated to your organization
- Visibility into hardware, control over maintenance
- For compliance/licensing requirements

---

- Supports: .NET, .NET Core, Node.js, Java, PHP, Python, Ruby
- Built-in auto-scaling and load balancing
- Deployment slots (staging → production)
- Integrates with GitHub, Azure DevOps

# 4. Storage Services

## Azure Storage Account
The foundational storage service — contains all Azure storage data objects.

### Storage Account Types

| Type | Supported Services | Use Case |
|------|-------------------|----------|
| **Standard general-purpose v2** | Blobs, Files, Queues, Tables | Most common, recommended |
| **Premium block blobs** | Block blobs only | Low-latency blob scenarios |
| **Premium file shares** | Azure Files only | High-performance file shares |
| **Premium page blobs** | Page blobs only | High-performance disks |

---

## Azure Blob Storage
**Object storage** for unstructured data (similar to AWS S3).

- Optimized for: images, videos, backups, logs, static files
- Access via HTTP/HTTPS, REST API, SDKs

### Blob Access Tiers

| Tier | Use Case | Access | Cost |
|------|----------|--------|------|
| **Hot** | Frequently accessed data | Immediate | Higher storage, lower access |
| **Cool** | Infrequently accessed (≥30 days) | Immediate | Lower storage, higher access |
| **Cold** | Rarely accessed (≥90 days) | Immediate | Lower still |
| **Archive** | Long-term retention (≥180 days) | Hours (rehydrate first) | Lowest storage, highest access |

### Blob Types
- **Block Blob** — Store text and binary data (most common)
- **Append Blob** — Optimized for append operations (logging)
- **Page Blob** — Random read/write (used for Azure VM disks)

---

## Azure Files
Fully managed **file shares** in the cloud accessible via SMB and NFS protocols.

- Mount on Windows, Linux, macOS
- Replace or supplement on-premises file servers

## Azure Queue Storage
Message queuing for asynchronous communication between app components.
- Store millions of messages
- Max message size: 64 KB

## Azure Table Storage
NoSQL key-attribute store for structured, non-relational data.
- Schemaless design
- Good for IoT data, user data

## Azure Disk Storage
**Managed disks** attached to Azure VMs (block storage).

| Type | IOPS | Use Case |
|------|------|----------|
| **Ultra Disk** | Up to 160,000 | Mission-critical, high performance |
| **Premium SSD v2** | Up to 80,000 | Production databases |
| **Premium SSD** | Up to 20,000 | Production workloads |
| **Standard SSD** | Up to 6,000 | Web servers, lightly used apps |
| **Standard HDD** | Up to 2,000 | Dev/test, backups |

---

## Storage Redundancy Options

| Option | Copies | Geographic Spread | SLA | Best For |
|--------|--------|------------------|-----|----------|
| **LRS** (Locally Redundant) | 3 | Same data center | 99.999999999% | Low cost, dev/test |
| **ZRS** (Zone Redundant) | 3 | 3 zones, same region | 99.9999999999% | High availability |
| **GRS** (Geo-Redundant) | 6 | 2 regions | 99.99999999999999% | DR protection |
| **GZRS** (Geo-Zone Redundant) | 6 | Zones + 2nd region | 99.99999999999999% | Maximum protection |
| **RA-GRS** | 6 | 2 regions + read access | — | Read from secondary |
| **RA-GZRS** | 6 | Zones + 2nd region + read | — | Max + read secondary |

> **Exam tip:** GRS/GZRS replicate to a **paired region**. Secondary is readable only with RA-GRS/RA-GZRS.

# 6. Networking Services

## Azure Virtual Network (VNet)
Your private, isolated network in Azure (similar to AWS VPC).

- Segment using **subnets**
- Control traffic with **Network Security Groups (NSGs)**
- Connect VNets using **VNet Peering**

### Key Networking Components

| Component | Description |
|-----------|-------------|
| **Subnet** | Segment a VNet into smaller address ranges |
| **NSG (Network Security Group)** | Stateless firewall rules (allow/deny) for subnets or NICs |
| **ASG (Application Security Group)** | Group VMs logically for NSG rules |
| **Route Table (UDR)** | Custom routing rules |
| **Azure Firewall** | Managed, stateful cloud firewall |
| **DDoS Protection** | Basic (free) or Standard (paid, advanced protection) |

---

## Connectivity Services

| Service | Purpose |
|---------|---------|
| **VPN Gateway** | Encrypted tunnel over public internet to Azure (site-to-site, point-to-site) |
| **Azure ExpressRoute** | Private, dedicated connection from on-prem to Azure (not over internet) |
| **Azure Virtual WAN** | Unified network hub for large-scale connectivity |
| **VNet Peering** | Connect two VNets (same or different regions) |
| **Azure Bastion** | Secure RDP/SSH to VMs without public IP |
| **Azure Private Link** | Access Azure services over private endpoint (no internet) |

### VPN Gateway vs ExpressRoute

| Feature | VPN Gateway | ExpressRoute |
|---------|------------|--------------|
| Connection | Over internet (encrypted) | Private, dedicated |
| Bandwidth | Up to 10 Gbps | Up to 100 Gbps |
| Latency | Variable | Consistent, low |
| Cost | Lower | Higher |
| Setup | Minutes | Weeks (physical circuit) |
| Use Case | Small orgs, remote users | Enterprise, compliance |

---

## Load Balancing & Traffic Management

| Service | Layer | Use Case |
|---------|-------|----------|
| **Azure Load Balancer** | Layer 4 (TCP/UDP) | Internal or public, high performance |
| **Application Gateway** | Layer 7 (HTTP/HTTPS) | Web apps, SSL termination, WAF |
| **Azure Front Door** | Layer 7 + Global | Global CDN + load balancer + WAF |
| **Traffic Manager** | DNS-level | Route based on geography, performance, priority |

# 7. Identity, Security & Compliance

## Microsoft Entra ID (formerly Azure Active Directory)
Microsoft's cloud-based **identity and access management** service.

- **Users, Groups, Applications**
- **Single Sign-On (SSO)** — one login for many apps
- **Multi-Factor Authentication (MFA)**
- **Conditional Access** — grant/block access based on conditions
- **B2B** — collaborate with external users (guest accounts)
- **B2C** — identity for customer-facing apps

### Entra ID vs On-Premises Active Directory

| Feature | Entra ID | On-Premises AD |
|---------|---------|----------------|
| Deployment | Cloud | On-premises |
| Auth Protocol | OAuth, OpenID Connect, SAML | Kerberos, NTLM |
| Structure | Flat (no OUs by default) | Hierarchical (OUs, GPOs) |
| Device Mgmt | Intune | Group Policy |
| Federation | Built-in | AD FS required |

---

## Authentication Methods

| Method | Description |
|--------|-------------|
| **Single Sign-On (SSO)** | One credential for multiple applications |
| **MFA** | Requires 2+ verification factors |
| **Passwordless** | Windows Hello, FIDO2, Authenticator App |
| **Conditional Access** | Policy-based access (location, device, risk) |

## Zero Trust Model
**"Never trust, always verify"**
- Verify explicitly (always authenticate and authorize)
- Use least privilege access
- Assume breach (minimize blast radius)

## Defense in Depth

```
Layer 1: Physical Security — Data center access
Layer 2: Identity & Access — Entra ID, MFA
Layer 3: Perimeter — DDoS, Firewall
Layer 4: Network — NSG, subnets, VPN
Layer 5: Compute — Defender for Servers, patching
Layer 6: Application — Secure SDLC, no vulnerabilities
Layer 7: Data — Encryption at rest and in transit
```

```
Management Groups
```

# 10. Pricing & Cost Management

## Azure Pricing Factors
- **Resource type** — Different services have different meters
- **Service tier** — Basic vs Standard vs Premium
- **Region** — Prices vary by region
- **Bandwidth** — Inbound is free; outbound data transfer costs
- **Reservation** — Commit 1 or 3 years for up to 72% savings
- **Azure Hybrid Benefit** — Use existing Windows Server / SQL Server licenses

## Pricing Models

| Model | Description | Savings | Best For |
|-------|-------------|---------|----------|
| **Pay-as-you-go** | No commitment, pay by second/hour | Baseline | Dev/test, variable workloads |
| **Reserved Instances** | 1 or 3 year commitment | Up to 72% | Steady production workloads |
| **Spot VMs** | Unused capacity, can be evicted | Up to 90% | Fault-tolerant, batch jobs |
| **Azure Hybrid Benefit** | Bring existing licenses | Up to 85% combined | Windows Server / SQL Server customers |
| **Dev/Test Pricing** | Discounted rates for dev/test | Varies | Non-production only |

## Service Level Agreements (SLAs)

- **SLA** = Microsoft's uptime/connectivity guarantee for a service
- Expressed as a **percentage** (e.g., 99.9%)
- Violations result in **service credits**

### Common SLA Values

| Uptime | Downtime/Month | Downtime/Year |
|--------|---------------|---------------|
| 99% | ~7.2 hours | ~3.65 days |
| 99.9% | ~43.8 minutes | ~8.76 hours |
| 99.95% | ~21.9 minutes | ~4.38 hours |
| 99.99% | ~4.4 minutes | ~52.6 minutes |
| 99.999% | ~26 seconds | ~5.26 minutes |

### Composite SLA (Multiple Services)
Multiply individual SLAs together:
```
Web App SLA (99.95%) × SQL Database SLA (99.99%) = 99.94% composite SLA
```
> Adding redundancy (availability zones) **increases** composite SLA.

### Preview Services
- Features in **preview** have **no SLA**
- Public preview = available but not production-ready
- General Availability (GA) = production-ready with SLA

---

## Azure Service Lifecycle

```
Private Preview → Public Preview → General Availability (GA)

Private Preview: Limited customers, testing only
Public Preview:  Anyone can use, no SLA, reduced pricing
GA:              Full SLA, full support, full pricing
```

## SLA Composite Example

```
If you have:
  - VM:  99.99% SLA (Availability Zones)
  - SQL: 99.99% SLA

Composite = 99.99% × 99.99% = 99.98%

To INCREASE SLA:
  - Add redundancy (more zones, more regions)
  - Add load balancers
  - Use higher-tier services

To DECREASE SLA:
  - Remove redundancy
  - Chain more dependent services
  - Use preview services (no SLA at all)
```

## Final Tips

- **Know the hierarchy:** Management Groups → Subscriptions → Resource Groups → Resources
- **Know the difference:** ExpressRoute (private) vs VPN Gateway (encrypted internet)
- **Know the difference:** Azure Policy (enforce rules) vs Azure Advisor (recommendations)
- **Know the difference:** ARM Templates (JSON/IaC) vs Azure Blueprints (governance packages)
- **Know the difference:** Defender for Cloud (posture) vs Sentinel (SIEM)
- **Always choose PaaS** when the question asks for "less management overhead."
- **Managed = PaaS**, Full control = IaaS (VMs)
- **Azure Functions** = event-driven serverless code
- **Logic Apps** = serverless workflow/integration
- **Cosmos DB** = global, multi-model, any scale NoSQL
- **Preview services = No SLA** — always remember this!
- **Inbound data transfer = Free**, Outbound = costs money
- **Reservations = up to 72% savings**, Spot = up to 90%
